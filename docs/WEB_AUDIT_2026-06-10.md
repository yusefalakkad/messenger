# Аудит WEB-мессенджера — финальный отчёт

_Сгенерирован 2026-06-10. Многоагентный аудит: 1 mapper + 9 параллельных finders (auth/chat/calls/media/e2e/state-sockets/ui-ux/security/build-perf) + adversarial verify по 2 линзам (correctness + reproducibility) на каждую находку. 68 поднято, 64 подтверждено, 4 опровергнуто._

## TL;DR

Подтверждено **3 P0**, **24 P1**, **25 P2**, **12 P3** (всего 64 находки из 9 категорий: calls, media, auth, build-perf, chat, e2e, state-sockets, ui-ux, security).

**Топ-3 риска:**
1. **Звонки физически не работают на медленных устройствах / при первом запросе разрешений** — оффер дропается до создания `pcRef.current` (CallOverlay race), `iceconnectionstatechange` не вешается, не отрабатывает auto-tearDown.
2. **Всё медиа сломано в нативной iOS-сборке** — `MEDIA_HOST` определён, но нигде не используется + GET `/media` требует Bearer/cookie, которых `<img>/<video>` не шлют, а phone-auth вообще не выставляет `refreshToken` cookie.
3. **Утечка данных предыдущего пользователя при перелогине в той же вкладке** — `logout()` не сбрасывает chat-store / call-store / outbox / socket / drafts; новый user видит чаты, превью и черновики старого.

## P0 — критично

### P0-1. Incoming WebRTC offer дропается до готовности `pcRef.current`
**Файл:** [CallOverlay.tsx:158](packages/web/src/components/call/CallOverlay.tsx)
**Симптом:** callee жмёт «Принять», UI обоих сторон висит, аудио/видео не идёт, через 30 с — таймаут.
**Причина:** `startPeer()` сначала `await getIceServers()` и `await getUserMedia()`, и только потом `pcRef.current = pc`. К этому моменту caller уже шлёт оффер (после `call:accepted`), но обработчик `call:signal` бэйлит на `if (!pc) return;` — нет очереди для оффера (только для ICE-кандидатов, и она тоже бэйлит).
**Что делать:** создавать `RTCPeerConnection` синхронно в самом начале `startPeer`, до любого `await`; ICE-сервера применять через `pc.setConfiguration({iceServers})` когда придут. Альтернативно — буфер `pendingSignals` до момента готовности `pc`.

### P0-2. `MEDIA_HOST` не используется → всё медиа сломано в Capacitor iOS
**Файл:** [config.ts:29](packages/web/src/lib/config.ts)
**Симптом:** в нативной сборке все фото/видео/голосовые/кружки — битые: WebView резолвит `/api/media/...` относительно `capacitor://localhost`.
**Причина:** `MEDIA_HOST` экспортируется, но `grep -rn MEDIA_HOST` даёт только определение. Везде в `<img>/<video>/<audio>` используется сырой `media.url` ([MessageBubble.tsx:171, :326, :449](packages/web/src/components/chat/MessageBubble.tsx), [ImageViewer.tsx:59](packages/web/src/components/chat/ImageViewer.tsx), [ProfilePanel.tsx:124](packages/web/src/components/profile/ProfilePanel.tsx)).
**Что делать:** хелпер `resolveMediaUrl(url)` в `config.ts`, использовать во всех точках рендера; либо абсолютный URL пекать на стороне стора при приёме сообщения от сокета.

### P0-3. Media GET требует Bearer/cookie, которых `<img>/<video>` не шлют
**Файл:** [media.routes.ts:15](packages/backend/src/routes/media.routes.ts)
**Симптом:** все медиа возвращают 401 в native-сборке и у phone-auth пользователей в вебе. Сломаны старые сообщения.
**Причина:** (1) middleware читает только заголовок `authorization` или cookie `refreshToken`; (2) `<img>` не проходит через axios-интерсептор; (3) [phoneAuth.controller.ts:25,44,69](packages/backend/src/controllers/phoneAuth.controller.ts) вообще не вызывает `res.cookie('refreshToken', …)`; (4) [api.ts:9](packages/web/src/lib/api.ts) выключает `withCredentials` в native. Все три класса юзеров видят 401.
**Что делать:** signed URL с `?t=<jwt>` для медиа (рекомендация), либо access_token через query, либо Service Worker, проксирующий `/api/media/`.

## P1 — серьёзно

### Calls

#### P1-1. `iceconnectionstatechange` listener никогда не вешается — auto-end на TURN failure dead code
**Файл:** [CallOverlay.tsx:213](packages/web/src/components/call/CallOverlay.tsx)
**Симптом:** при ICE failed (TURN недоступен, смена сети) overlay висит вечно с замороженным видео.
**Причина:** эффект читает `pcRef.current` синхронно после смены `active.callId`, но `startPeer` асинхронный — `pc` ещё нет. Эффект бэйлит и больше не перезапускается.
**Что делать:** вешать `pc.oniceconnectionstatechange` прямо внутри `startPeer` после `pcRef.current = pc` (рядом с `pc.ontrack`/`pc.onicecandidate`).

#### P1-2. Incoming UI callee'а виснет навсегда при отмене caller'ом до accept
**Файл:** [CallOverlay.tsx:200](packages/web/src/components/call/CallOverlay.tsx)
**Симптом:** caller отменил вызов до того, как callee нажал «Принять» — у callee incoming overlay не закрывается.
**Причина:** бэкенд эмитит `call:ended` только в `call:${callId}` room ([socket.server.ts:302](packages/backend/src/socket/socket.server.ts)), а callee туда не вступал. На фронте таймаут есть только для `outgoing`.
**Что делать:** (а) симметричный 45-сек таймаут для `incoming`; (б) бэкенд должен дополнительно эмитить `call:ended` в `user:${peerId}` или пре-джойнить callee в room на `call:incoming`.

#### P1-3. Старый pc + камера/микрофон не теряются при back-to-back звонках
**Файл:** [CallOverlay.tsx:194](packages/web/src/components/call/CallOverlay.tsx)
**Симптом:** камера-LED светится после второго звонка, два `RTCPeerConnection` живут параллельно.
**Причина:** useEffect `if (active) startPeer(...)` не возвращает cleanup. `track.stop()` и `pc.close()` старых не вызываются.
**Что делать:** возвращать `tearDown()` как cleanup; либо в начале `startPeer` сначала `tearDown()` старых ссылок.

#### P1-4. Нет busy/concurrent-call handling — второй incoming перезатирает первый
**Файл:** [CallOverlay.tsx:26](packages/web/src/components/call/CallOverlay.tsx) + [call.store.ts:63](packages/web/src/stores/call.store.ts)
**Симптом:** во время активного звонка приходит второй — UI показывает оба набора кнопок, имя меняется на нового вызывающего, случайный accept ломает первый звонок.
**Причина:** `setIncoming` пишет без проверки, рендер-ветки `incoming!=null` и `active!=null` независимы, селектор `peerName` всегда отдаёт приоритет incoming.
**Что делать:** в socket-хэндлере `call:incoming`: если уже есть `active || outgoing || incoming` — сразу `call:reject` для нового, toast «Пропущенный от X».

#### P1-5. Нет рингтона при incoming — на фоне теряются звонки
**Файл:** [socket.ts:123](packages/web/src/lib/socket.ts)
**Симптом:** при свёрнутой/фоновой вкладке incoming звонок — без звука.
**Причина:** хэндлер `call:incoming` только пишет в стор. Для сравнения, `message:new` ([socket.ts:82](packages/web/src/lib/socket.ts)) вызывает `playNotificationSound()`.
**Что делать:** loop `<audio>` в `CallOverlay` пока `incoming` не null; на mobile/PWA — Notification с `requireInteraction: true`.

### Media

#### P1-6. Видео из файлов без poster/duration — пузырёк показывает серый плейсхолдер
**Файл:** [MessageInput.tsx:523](packages/web/src/components/chat/MessageInput.tsx)
**Симптом:** отправленное «как файл» видео показывает заглушку с одинокой Play-иконкой, нет длительности.
**Причина:** `handleMediaSend` для `type='video'` не генерирует постер/dimensions/duration в отличие от `handleVideoRecorded` ([:464-504](packages/web/src/components/chat/MessageInput.tsx)).
**Что делать:** скрытый `<video>` из `URL.createObjectURL(file)` → `loadedmetadata` → `seeked` → canvas → JPEG poster через `/media/upload/image`; параллельно сохранить `videoWidth/Height/duration` в `mediaData`.

### Auth

#### P1-7. После /auth/refresh socket продолжает работать со старым токеном
**Файл:** [api.ts:54](packages/web/src/lib/api.ts)
**Симптом:** после тихого refresh любая реконнект-волна (сеть, рестарт сервера) выкидывает юзера в «оффлайн» без видимого индикатора до hard-reload.
**Причина:** `setAccessToken` обновляет стор, но не трогает `socket.auth`. socket.io читает auth payload один раз в `initSocket()`.
**Что делать:** после успешного refresh — `const s = getSocket(); if (s) { s.auth = { token: newToken }; if (!s.connected) s.connect(); }`.

#### P1-8. Refresh-failure logout оставляет dead socket в reconnect loop
**Файл:** [api.ts:60](packages/web/src/lib/api.ts)
**Симптом:** на /auth висит шумный reconnect с error-тостами; если юзер логинится снова — получаем два socket'а на одних handlers.
**Причина:** интерсептор не зовёт `disconnectSocket()`. Только кнопка Logout в Sidebar делает это правильно.
**Что делать:** перенести `disconnectSocket()` внутрь `auth.store.logout()` (lazy import), чтобы все пути logout'а были атомарны.

#### P1-9. PhoneAuthForm не шлёт deviceId — каждый login = новая orphan сессия
**Файл:** [PhoneAuthForm.tsx:111](packages/web/src/components/auth/PhoneAuthForm.tsx)
**Симптом:** таблица `Session` растёт бесконтрольно, «активные устройства» вранье, старые refresh tokens живут 30 дней.
**Причина:** нет поля `deviceId` в body `/verify` и `/complete-profile`; бэк ([phoneAuth.controller.ts:9](packages/backend/src/controllers/phoneAuth.controller.ts)) фоллбэчит на `uuidv4()` каждый раз — `deleteMany where deviceId` никогда не матчит.
**Что делать:** читать/создавать `localStorage.getItem('deviceId') ?? uuidv4()` и слать с `deviceName`, как в [LoginForm.tsx:54-63](packages/web/src/components/auth/LoginForm.tsx).

#### P1-10. Logout не ресетит chat-store — данные A видит B
**Файл:** [auth.store.ts:50](packages/web/src/stores/auth.store.ts) (дубль: e2e #1, state-sockets #1)
**Симптом:** после смены юзера в одной вкладке B на сотни мс видит чаты, превью, unread, draft'ы A. Зашифрованные сообщения молча падают на расшифровке.
**Причина:** `logout()` чистит только auth-стор + keyVault + iceServers. `useChatStore`, `useCallStore`, react-query cache, `pendingOutbox`, `localStorage.draft:*` — всё остаётся.
**Что делать:** общий `resetAppState()`: chat-store → initial, `clearCall()/clearGroupCall()`, `queryClient.clear()`, `disconnectSocket()`, очистка `pendingOutbox`/`pendingAcks`/`hadInitialConnectEver`, удаление всех `draft:*` ключей (либо `draft:<userId>:<chatId>` scoping).

#### P1-11. complete-profile race: verify token сжигается до проверки username
**Файл:** [phoneAuth.service.ts:204](packages/backend/src/services/phoneAuth.service.ts)
**Симптом:** username занят → ошибка → юзер меняет → `VERIFY_TOKEN_INVALID`, тупик с крутящимся «Не удалось завершить регистрацию».
**Причина:** `consumeVerifyToken` одношотовый, вызван первой строкой; проверки уникальности — после.
**Что делать:** `peekVerifyToken` без удаления → все проверки → `consume` непосредственно перед `prisma.user.create`. Клиент: на `VERIFY_TOKEN_INVALID` возвращать в шаг `phone` с тостом.

### Chat

#### P1-12. Потеря сообщений при chat-open / resync (гонка с live сокетом)
**Файл:** [socket.ts:277](packages/web/src/lib/socket.ts)
**Симптом:** сообщения, пришедшие пока GET `/chats/:id/messages` в полёте, молча исчезают и из UI, и из памяти.
**Причина:** `setMessages(chatId, data.data)` ЗАМЕНЯЕТ массив; параллельный `addMessage` из сокета затирается серверным снапшотом.
**Что делать:** `mergeMessages` с dedupe по `id` + сохранение локальных, отсутствующих в серверном payload. То же в [ChatWindow.useEffect](packages/web/src/pages/ChatWindow.tsx).

#### P1-13. Reply preview зашифрованного сообщения показывает base64 ciphertext
**Файл:** [socket.server.ts:486](packages/backend/src/socket/socket.server.ts)
**Симптом:** reply-quote в пузырьке/инпуте показывает сырую шифрку вместо «🔒 Зашифрованное сообщение».
**Причина:** Prisma `include` для `replyTo` не включает `encrypted` (и `nonce`); `formatReplyPreview` без флага `encrypted` падает в `formatMessagePreview` → `msg.content`.
**Что делать:** добавить `encrypted: true, nonce: true, media: ...` в `replyTo: { select: ... }` везде, где он отдаётся (socket + REST).

### E2E

#### P1-14. Forward зашифрованного сообщения в не-E2E чат отправляет plaintext без предупреждения
**Файл:** [ForwardDialog.tsx:49](packages/web/src/components/chat/ForwardDialog.tsx)
**Симптом:** перешёл E2E-сообщение в группу — секрет загрузился на сервер в открытом виде.
**Причина:** decrypt безусловный; в `else`-ветке (не-E2E target) — `sendMessage({content: plainText})` без модала и без флага.
**Что делать:** если `message.encrypted && !isChatE2E(target)` — модал «Текст будет виден серверу, подтвердить?», по умолчанию refuse.

#### P1-15. Подписи к медиа в E2E чате идут без шифрования; сайдбар светит caption verbatim
**Файл:** [MessageInput.tsx:534](packages/web/src/components/chat/MessageInput.tsx)
**Симптом:** в E2E direct chat фото+подпись = подпись в БД в открытом виде; сайдбар: `📷 <caption>`.
**Причина:** `handleMediaSend` не зовёт `encryptText`, не ветвится на `isChatE2E`. `messagePreview.ts:18-19` рендерит `msg.content` без проверки `encrypted` для типа image/video.
**Что делать:** шифровать caption для media в E2E чате (как text); preview честно возвращает `📷 🔒` / `🎬 🔒` при `encrypted`.

#### P1-16. Drafts в E2E чате пишутся в localStorage в открытом виде
**Файл:** [MessageInput.tsx:117](packages/web/src/components/chat/MessageInput.tsx)
**Симптом:** черновики переживают logout, читаются следующим юзером того же браузер-профиля.
**Причина:** `useEffect` пишет `localStorage["draft:<chatId>"]` без awareness E2E и без cleanup при logout.
**Что делать:** scope ключа `draft:<userId>:<chatId>` + удаление всех `draft:*` в logout; либо для E2E — только in-memory (zustand slice).

### State / Sockets

#### P1-17. Stale outbox после logout — pending-сообщения A улетят под сессией B
**Файл:** [socket.ts:252](packages/web/src/lib/socket.ts)
**Симптом:** A офлайн набрал сообщений → logout → B логинится → `resyncAfterReconnect` шлёт их под B.
**Причина:** `disconnectSocket` не чистит `pendingOutbox` / `pendingAcks`; `hadInitialConnectEver` остаётся true.
**Что делать:** в `disconnectSocket`: `pendingAcks` (clearTimeout каждый) + `pendingOutbox.clear()` + `hadInitialConnectEver = false`. Опц.: ключ `(userId, clientMsgId)` + фильтр на resync.

#### P1-18. Outbox-resend не дренируется при ПЕРВОМ connect — сообщения, набранные офлайн до первого подключения, теряются навсегда
**Файл:** [socket.ts:219](packages/web/src/lib/socket.ts)
**Симптом:** открыл приложение офлайн, набрал, дождался подключения — ничего не ушло.
**Причина:** `resyncAfterReconnect` (где живёт drain) гейтнут `if (hadInitialConnectEver) ... else { hadInitialConnectEver = true; return }`.
**Что делать:** вынести drain в отдельную функцию, звать в обеих ветках.

### Build / Perf

#### P1-19. livekit-client + framer-motion в main-бандле на каждом роуте (нет code splitting)
**Файл:** [App.tsx:9](packages/web/src/App.tsx)
**Симптом:** AuthPage / Landing качают `~1.17 MB index.js` со всем чатом + LiveKit'ом.
**Причина:** статические импорты `CallOverlay` / `GroupCallView`; нет `React.lazy`, нет `manualChunks` в [vite.config.ts](packages/web/vite.config.ts).
**Что делать:** `React.lazy` для `CallOverlay`/`GroupCallView` (рендерить за `isAuthenticated && (active||group)`); `manualChunks: { livekit, motion, icons }`; lazy AuthPage/LandingPage.

## Что НЕ нашли (или отказались подтвердить)

Аудит фокусировался на: **calls, media, auth, chat, e2e, state/sockets, ui-ux, build/perf, security**. По следующим участкам **финальная сетка пустая** — что не значит «всё ок», но скептики отбросили предложенные находки как ложные:

- **CSP / X-Frame-Options / clickjacking** — все эти заголовки уже выставлены на уровне nginx ([nginx.conf:58-63](nginx/nginx.conf)); в `index.html` их быть и не должно.
- **`renderRichText` regex stateful** — false alarm, `MENTION_RE` пересоздаётся.
- **Stale `call:signal` handler** после смены `callId` — отбит callId guard на [CallOverlay.tsx:160](packages/web/src/components/call/CallOverlay.tsx).
- **Группы (group chat)** — отдельно глубоко не копали; LiveKit-флоу (GroupCallView, GroupCallPill) только косвенно затронуты через P1-19. Стоит отдельным проходом.
- **Backend пермишены/CSRF/CORS** — за исключением P0-3 и P1-11; полный аудит backend security вне scope этого прохода.
- **Платёжка / push-нотификации** end-to-end (только sw.js handler и отсутствие звонкового рингтона на клиенте).
- **Accessibility / i18n** — вообще не смотрели.

## Открытые вопросы

1. **Media auth: какой механизм signed URL?** — варианты: (а) `?t=<short-jwt>` query параметр, генерируется при создании сообщения и валится на сервере без БД-хита (HMAC + expiry), (б) S3/MinIO presigned URLs из minio.ts, (в) Service Worker proxy. Нужно решение по архитектуре и TTL. Зависит — успеваем ли продлевать у юзера, который смотрит старое фото 2 недели спустя.
2. **`MEDIA_HOST` vs absolute URLs в payload** — пекать абсолютный URL на бэке (брейкинг для существующих клиентов?) или клиентский helper. Если signed URL делается — то URL уже всегда абсолютный и пекать имеет смысл.
3. **Busy handling protocol** — нужен ли `call:busy` событие на бэке отдельно (контракт + миграция socket-протокола), или достаточно автоматического `call:reject` с reason='busy' на клиенте.
4. **Forward в не-E2E чат** — refuse hard или подтверждение с галкой «понимаю риски»? UX-решение пользователя.
5. **Drafts в E2E чате** — полностью убрать из localStorage (потеря при reload) или зашифровать собственным ключом? Trade-off privacy vs UX.
6. **deviceId persist** — оставить в localStorage (теряется при clear-data) или поднимать в IndexedDB через keyVault? Завязано на «active devices» UX.
7. **ECDH → HKDF миграция** — есть ли существующие E2E чаты в проде, которые нужно поддерживать обратно совместимо? Если да — нужен версионный envelope (`v1` raw, `v2` HKDF).
8. **Virtualization** — `react-virtuoso` ок или хочется свой? Влияет на P2-23 объём работы.
9. **PWA push ringtone iOS** — Web Push на iOS PWA требует `requireInteraction` + media-controlled audio context; нужно подтвердить, что target юзеры — Capacitor native, не PWA, чтобы выбрать стратегию.
10. **strict: true миграция** — пакетно или package-by-package? 11 текущих ошибок — это нижняя оценка; реальное число при `strict: true` может быть существенно выше.
